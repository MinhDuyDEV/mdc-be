## PURPOSE

This directory stores versioned database migrations generated by Prisma. Each migration is a timestamped folder containing a `migration.sql` file that represents a single schema change. Migrations are immutable once committed and form the audit trail of all database structure changes. This is the authoritative record of schema evolution and must never be manually edited after deployment.

## KEY FILES & SUBDIRECTORIES

| Item | Purpose |
|------|---------|
| `20260516080000_init_baseline/` | Initial baseline migration. Creates all core tables (users, refresh_tokens, audit_logs, outbox_events, outbox_dead_letters, idempotency_keys), enums (UserStatus, OutboxEventStatus), indexes, and foreign keys. |
| `20260516080000_init_baseline/migration.sql` | SQL DDL statements for the baseline schema. Includes CREATE TABLE, CREATE INDEX, CREATE TYPE (enums), and ALTER TABLE (foreign keys). |
| `_migration_lock.toml` | Lock file (auto-generated by Prisma) that prevents concurrent migrations. Do not edit manually. |

## MIGRATION STRUCTURE

Each migration folder follows the naming convention: `YYYYMMDDHHMMSS_<description>/`

- **Timestamp prefix** — Ensures chronological ordering and uniqueness.
- **Description** — Human-readable summary of the change (e.g., `init_baseline`, `add_user_preferences`, `rename_column_email_to_email_address`).
- **migration.sql** — The actual SQL to apply. Generated by Prisma; never edit manually after commit.
- **_migration_lock.toml** — Prisma internal lock file; ignore.

```
├── migration.sql          # SQL DDL for this migration
└── _migration_lock.toml   # Prisma lock (auto-generated)
```

## AI AGENT INSTRUCTIONS

### DO NOT Manually Edit Migrations

**Critical Rule:** Once a migration is committed and pushed, it is immutable. Never edit a `.sql` file in a migration folder. Doing so breaks the migration history and causes deployment failures.

### Creating a New Migration

1. **Modify `schema.prisma`** — Add/update models, enums, relations, or field attributes in the parent `../schema.prisma`.
2. **Generate migration** — Run:
   ```bash
   npx prisma migrate dev --name <description>
   ```
   This creates a new timestamped folder in `migrations/` with the generated SQL.
3. **Review the SQL** — Inspect the generated `migration.sql` file:
   - Verify table/column names match schema intent.
   - Check indexes are created for foreign keys and frequently queried fields.
   - Ensure constraints (UNIQUE, NOT NULL, CHECK) are correct.
   - Confirm data transformations (if any) are safe.
4. **Test locally** — Apply the migration to a local PostgreSQL instance:
   ```bash
   npx prisma migrate dev
   ```
   Verify the schema matches expectations and no errors occur.
5. **Commit both files** — Always commit `schema.prisma` + the new migration folder together:
   ```bash
   git add prisma/schema.prisma prisma/migrations/<new-folder>/
   git commit -m "feat(db): <description>"
   ```

### If a Migration Fails

1. **Inspect the error** — Read the error message carefully; it usually indicates which SQL statement failed.
2. **Fix `schema.prisma`** — Correct the schema definition.
3. **Mark migration as rolled back** — Run:
   ```bash
   npx prisma migrate resolve --rolled-back <migration-name>
   ```
   This removes the failed migration from the `_prisma_migrations` table.
4. **Create a new migration** — Run `npx prisma migrate dev --name <corrected-description>` to generate a corrected migration.
5. **Commit the new migration** — Do not edit the failed migration; create a new one.

### Deploying Migrations to Production

1. **Ensure all migrations are committed** — No uncommitted changes in `prisma/migrations/`.
2. **Run migrations** — In the production environment:
   ```bash
   npx prisma migrate deploy
   ```
   This applies all pending migrations in order.
3. **Verify schema** — After deployment, confirm the schema matches expectations:
   ```bash
   npx prisma db execute --stdin < <(echo "SELECT * FROM information_schema.tables WHERE table_schema = 'public';")
   ```

### Handling Enum Changes

- **Adding a new enum value** — Safe. Generate a migration; Prisma will add the value to the enum type.
- **Removing an enum value** — Requires data migration. First, update all rows using the old value to a new value, then remove the enum value in a separate migration.
- **Renaming an enum value** — Requires data migration. Update rows, then rename the enum value.

### Handling Data Migrations

If a migration requires data transformation (e.g., backfilling a new column):

1. **Add the column** — Modify `schema.prisma` to add the new field.
2. **Generate migration** — Run `npx prisma migrate dev --name <description>`. Prisma generates the ADD COLUMN statement.
3. **Edit the migration SQL** — Add a data transformation step (e.g., `UPDATE table SET new_column = computed_value WHERE ...;`).
4. **Test thoroughly** — Apply to a local database and verify data integrity.
5. **Commit and deploy** — Follow standard deployment process.

### Viewing Migration History

- **List all migrations** — Check the `migrations/` directory or run:
  ```bash
  npx prisma migrate status
  ```
- **View applied migrations** — Query the `_prisma_migrations` table in the database:
  ```sql
  SELECT * FROM _prisma_migrations ORDER BY finished_at DESC;
  ```

## COMMON PATTERNS

### Transactional Outbox Pattern

The `outbox_events` and `outbox_dead_letters` tables implement the transactional outbox pattern for reliable event publishing:

1. **Write event** — Insert into `outbox_events` in the same transaction as the business operation.
2. **Poll and process** — Background worker polls `outbox_events` where `status = 'PENDING'` and `available_at <= now()`.
3. **Lock and publish** — Worker locks the event (`locked_at`, `locked_by`), publishes it, and updates `status = 'PROCESSED'`.
4. **Dead letter** — If publishing fails after max retries, insert into `outbox_dead_letters` for manual inspection.

### Idempotency Pattern

The `idempotency_keys` table prevents duplicate request processing:

1. **Check key** — On request, check if `(scope, key)` exists in `idempotency_keys`.
2. **Return cached response** — If found and not expired, return the cached `response_body`.
3. **Process and cache** — If not found, process the request, store the result in `idempotency_keys`, and return the response.
4. **Cleanup** — Periodically delete expired keys where `expires_at < now()`.

### Audit Logging Pattern

The `audit_logs` table tracks all significant actions:

1. **Insert audit record** — After a domain operation, insert an `AuditLog` with action, entityType, entityId, metadata, and actor info.
2. **Query history** — Retrieve audit history by entityType/entityId or by actor for compliance/debugging.
3. **Indexes** — Composite indexes on (entityType, entityId) and createdAt enable efficient range queries.

## GOTCHAS

- **Migrations are immutable** — Once committed and deployed, never edit a migration file. Create a new migration instead.
- **Timestamp uniqueness** — Prisma uses the current timestamp to name migrations. If two migrations are created within the same second, the second will fail. Manually adjust the timestamp if needed.
- **Foreign key constraints** — Ensure foreign key columns exist before adding constraints. Prisma generates these in the correct order, but manual edits can break this.
- **Enum type changes** — PostgreSQL enums cannot be modified in-place. Removing or renaming enum values requires creating a new type and migrating data.
- **Index naming** — Prisma auto-generates index names. For clarity, use explicit names in `schema.prisma` with `@@index([field], name: "idx_custom_name")`.
- **Concurrent migrations** — The `_migration_lock.toml` file prevents concurrent migrations. If a migration is interrupted, manually delete the lock file and retry.
- **Large data migrations** — For tables with millions of rows, data migrations can lock the table and cause downtime. Consider batching updates or using a separate tool.
